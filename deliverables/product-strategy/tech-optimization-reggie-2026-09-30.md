## 📌 TL;DR（执行摘要）

- **核心诊断**：Reggie 是一套"工程地基偏弱、但扩展范式良好（支付/AI 已有接口+工厂+DB 配置驱动）"的餐饮管理系统。最大可扩展性瓶颈是 **Session 内存态（无法水平扩容）**，最大稳定性隐患是 **Redis 池仅 8 / DB 池仅 20 + 同步重任务阻塞 HTTP 线程**，最大正确性风险是 **租户隔离白名单表绕过（11 张，其中 2 张物理无 tenant_id 待补列；ai_provider_config 已确认系统级全局表保留）、空上下文静默返回空集**。
- **关键决策**：采用 **"先地基、后护城河、竞争力给足权重"** 双线策略——P0 工程健康（会话无状态化、并发解耦、异步化、测试 CI、租户强校验）前置收敛；P0 竞争力（多租户 SaaS 化 + 全渠道"四通"适配器）与地基重叠推进，命中"连锁数据自主 / 信创私有化 / 规避平台抽佣"三大商家痛点。
- **预期价值**：稳定性对标竞品最大短板（卡顿/丢单/断网）；撬动约 **320 亿餐饮 SaaS** 市场与 **AI 渗透率 15%→50%** 红利；私域复购 **21%→40–70%**、获客成本 **52→8 元**；出餐提速 **15–30%**；多平台错发率 **2.3%→趋零**。
- **投入与周期**：约 **116–164 人周（≈2.5–3.5 人年，3–5 人团队）**，分 **M1–M9 共 9 个里程碑（2026Q4–2028Q4）**。
- **下一步**：先立项 M1 地基 I（会话 Redis 化 R-01 / 限流旁路 R-02 / 租户强校验 R-21），同步确认"分账资金通道后置、信创目标栈、四通同步粒度"三项待决假设。

## 〇、定位修正与优先级再校准（2026-09-30 用户澄清）

**澄清**：Reggie 不是"去做一个与美团 / 客如云 / 哗啦啦竞争的 SaaS 平台"，而是**给餐饮商家"自己部署、自己用"的开源 / 可二开系统**——核心价值主张 = 帮商家避开封闭系统的高费用与"无法自定义"。

**对前文假设的影响**：初稿部分沿用了"多租户云 SaaS + 订阅计费"的视角，与本定位不符，需再校准：

| 原假设 | 校准后 |
|---|---|
| 目标 = 多租户 SaaS 平台，按订阅收费 | 目标 = 单实例自托管，商家自行部署 / 二开；不做平台化订阅计费 |
| R-14 原"多租户 SaaS 平台" | 修正为"单实例内多租户隔离（直营 / 加盟 / 租用等不同合同关系）+ 总部-门店管控 + 按合同类型分账结算"；去掉的是"公有云 SaaS 订阅平台 + 我们收订阅费"，**不是**多租户隔离本身——租用 / 租赁店铺使多租户成为必需 |
| 信创 / 等保 / 云原生（R-20）作为 P2 护城河 | 降级为**按需可选项**，除非目标客户含大型 / 国企餐饮 |
| 可维护性 / 可扩展性权重居中 | **上调**：可定制 = 产品承诺本身，上帝类拆分（R-08）、CI/测试（R-10）、文档准确（R-12）、开放 API + 插件（R-18）成为差异化使能项 |
| R-15 全渠道四通、R-16 会员私域（沿用） | **保持高优且更贴合**：自托管系统仍需聚合美团 / 饿了么 / 抖音订单（用平台流量、自己掌握运营与数据），并自建私域会员以规避平台锁定 |

**不变（仍前置）**：P0 工程健康地基（R-01 会话无状态 / 水平扩容、R-02/R-05 并发解耦、R-06 异步化、R-10 测试 CI、R-21 租户强校验）。小商家服务器弱、自托管系统一旦卡顿 / 丢单即不可用，稳定性比"多租户"更基础。

**修正后的优先级主线**：先 P0 工程健康地基（含租户强校验 R-21）→ 再 P0 多租户（直营/加盟/租用等合同差异）+ 全渠道四通（R-15）+ 会员私域（R-16）→ P1"自托管定制力"（上帝类拆分 + CI + 文档 + 开放 API/插件范式，R-08/R-10/R-12/R-18）→ P1 按合同类型分账结算 → 信创 / 等保按需（R-20）。

## 〇·1 产品目标（3 个清晰正交的目标，对齐"提升产品竞争力"）

> 自托管定位下（商家自己部署 / 二开，绕开封闭平台高费用与不可定制），三条**正交**主线：互不重叠、可独立度量、不可互相替代。

| # | 目标 | 对齐痛点 / 证据 | 关键交付（主要 R） | 可衡量北极星 |
|---|------|----------------|-------------------|-------------|
| **G1 工程健康地基** | 消除稳定性 / 可扩展性 / 可维护性债务，使自托管实例在弱服务器上仍"不卡顿、不丢单、不断网可用" | 竞品最大槽点①稳定性（卡顿 / 丢单 / 断网）；数析：Session 内存态、Redis 池 8 / DB 池 20、上帝类 | R-01 会话无状态 / R-02 限流旁路 / R-05 权限缓存 / R-06 异步化 / R-10 测试 CI / R-21 租户强校验 | 无损滚动发布达成；P0 工程健康 100% 上线；Redis/DB 抖动下 HTTP 线程零阻塞 |
| **G2 渠道与运营竞争力** | 全渠道"四通"聚合接单 + 多租户（不同合同关系）隔离与总部-门店管控 + 按合同分账，命中"连锁数据自主 / 管控 / 规避抽佣" | 瑞思：多平台日均 2h、错发 2.3%、费率 18–25%；竞析护城河"规避平台抽佣 / 数据自主" | R-15 四通 / R-14 多租户（直营·加盟·租用·联营·代销）+ 分账 / R-21 | 多平台错发 2.3%→趋零；平台抽佣 18–25%→0（自托管流量自有）；连锁门店统一管控覆盖 |
| **G3 私域与智能竞争力** | 会员私域基座 + AI/BI 模块化，使商家"自己掌握运营与数据"，规避平台锁定 | 瑞思：私域复购 40–70% vs 21%、获客 8 vs 52 元；AI 渗透率 15%→50%；竞析护城河"数据自主可控" | R-16 会员私域 / R-17 AI·BI 模块化 | 私域复购 21%→40–70%；获客成本 52→8 元；AI 经营助手商家数对标 54.9 万 |

**正交性说明**：G1=技术健康（内部地基）/ G2=外部连接与多主体管控（横向渠道 + 纵向管控）/ G3=数据资产与智能（纵向增值）。三者互不替代——没 G1 则 G2/G3 在弱服务器上不稳定；没 G2 则流量被平台锁定；没 G3 则只剩"便宜稳定"而无增值壁垒。

## 〇·2 用户故事（3–5 个场景，覆盖商家与消费者）

> 覆盖四类商家（小单店 / 连锁 / 外卖专营 / 茶饮咖啡）+ 一类消费者（C 端），均锚定瑞思客群分层与痛点强度。

- **US-1 小单店自托管商家（张老板 · 中小单店）**：作为在普通服务器自托管单店的老板，我希望高峰时段系统不卡顿、Redis 抖动 / 断网时也不丢单、能无损重启升级，以免出餐慢 15–30% 与丢单致客诉。（驱动：R-01 无状态会话 / R-02 限流旁路 / R-06 异步化；对标竞品槽点①稳定性）
- **US-2 连锁品牌老板（李总 · 连锁）**：作为一个实例内同时有直营、加盟、租用门店的连锁老板，我希望各门店数据严格隔离、总部统一下发菜单 / 库存 / 看板，并按加盟合同自动分账结算，以免多系统割裂、算错账与加盟商数据串看。（驱动：R-14 多租户合同差异 + R-21 租户强校验 + 按合同分账）
- **US-3 多平台外卖专营店（王店 · 外卖专营）**：作为同时做美团 / 饿了么 / 抖音的专营商家，我希望三方订单在一个屏聚合接单、出餐状态自动回传平台，以免日均 2 小时跨平台搬运、2.3% 错发与 18–25% 平台费率吞噬利润。（驱动：R-15 全渠道四通）
- **US-4 茶饮咖啡店主（赵姐 · 茶饮咖啡）**：作为茶饮店主，我希望有储值 / 积分 / 企微私域会员并叠加 AI 推荐与定价，以免被平台抽佣锁定、复购长期停留在 21%。（驱动：R-16 会员私域 / R-17 AI·BI）
- **US-5 C 端消费者（小陈 · 点餐用户）**：作为点餐用户，我希望首屏加载快（43.2% 提及率 TOP1 痛点）、支付环节不流失（34%）、配送可实时可视化，以免因卡顿与不确定性 abandonment。（驱动：R-01 无状态 + 缓存 / R-06 异步降首屏 / C 端加载与支付优化）

## 一、代码架构与实现现状（数析证据，带文件引用）

> 探查范围：`src/main/java`（869 个 .java / 约 12.2 万行）、`src/main/resources`、`db/`、`pom.xml`。量化信号：39 个业务模块目录、103 个 Controller、117 个 `@Mapper`、26 个 `@Scheduled`、9 个 `@Async`、4 个 `@Cacheable`（仅 2 个缓存域真用）、19 处 `setIfAbsent` 分布式锁、最大类 `OrderServiceImpl` 2269 行。

### 1.1 性能维度
| 关键发现 | 证据 | 影响 | 建议 |
|---|---|---|---|
| 会话为 Servlet 内存 `HttpSession` | `LoginCheckFilter.java:78-100`，`application.yml` 仅配 timeout/http-only/same-site | 水平扩容必须 sticky session，无法无损滚动发布——**最大可扩展性瓶颈** | R-01 会话 Redis 化 / 无状态鉴权 |
| Redis lettuce 池 `max-active=8`，限流 Lua 在请求线程同步执行 | `application-dev.yml:43-59`、`RateLimitAspect` | 高并发下 8 连接 + 3s max-wait 成瓶颈，Redis 抖动直接阻塞 HTTP 线程 | R-02 池扩容 + 限流旁路化 |
| Druid `max-active=20`、`max-wait=60000ms`，未开预编译/remove-abandoned | `application-dev.yml:11-24`；Tomcat 200 线程 vs DB 池 20 | DB 池先成瓶颈，慢 SQL 占满后 200 线程排队 | R-03 池+预编译调优 |
| `disableCachingNullValues()` 穿透风险；`permissions` 缓存域死配置 | `RedisConfig.java:163,175`；全仓仅 4 处 `@Cacheable` | 大量不存在 key 穿透到 DB；死配置误导 | R-04 穿透防护 + 清理 |
| `PermissionServiceImpl` 类级 `@Transactional`，只读也进事务 | `PermissionServiceImpl.java:34,54-56` | 每次鉴权请求都开 DB 事务查权限表 | R-05 权限缓存化 + 事务下沉 |
| 26 `@Scheduled` 共用 3 线程池；19 处 `setIfAbsent` 锁散落无看门狗 | `SchedulingConfig.java:40`、`OrderTimeoutTask.java:356` 等 | 长任务互相阻塞；多实例可能重复执行 | R-07 分组线程池 + 统一锁看门狗 |

## 二、目标市场与竞争态势（瑞思 + 竞析证据）

### 2.1 市场规模与客群（瑞思）
- **大盘**：全国餐饮商户 **757.77 万**（关店率 49.1%，对"便宜/稳"敏感）；外卖市场约 **1.27 万亿**（占餐饮 22.8%），用户 **5.92 亿**；连锁化率 **21%(2024)→25%**；**数字化已实施仅 28.2%，但有意向 69%** → 巨大增量渗透空间。
- **客群诉求分层**：中小单店（轻/稳/便宜，扫码点餐+基础外卖）、连锁（多门店统一管控+分账+统一菜单库存+看板）、外卖专营（多平台聚合+出餐快+自配送降本）、团餐（供应链+食安溯源）、茶饮咖啡（会员+跨端+AI 推荐）。

### 2.2 竞品全景与对比矩阵（竞析）
| 竞品 | 定位 / 规模 | Reggie 相对空白 | Reggie 可切护城河 |
|---|---|---|---|
| 美团餐饮系统 | 活跃门店 80万+，月费 298–698 + 抽佣 8–15%，强绑定无私域 | 全渠道、流量、生态规模 | 零许可费、数据自主、规避抽佣、私有部署 |
| 饿了么 Napos | 阿里系，AI 饿小味 | AI 营销、平台流量 | 信创私有化、不绑定平台 |
| 客如云 | 阿里软硬一体 | 硬件生态、品牌势能 | 可深度二开、成本结构 |
| 哗啦啦 | 2023–24 资金危机，信任受损 | 规模客户 | 资金/数据自主可控（私有部署信任） |
| 有赞 | 三店一体/外卖通 300 元/店/年，600+ 应用生态 | 开放生态、会员私域、应用市场 | 零许可费、深度二开、数据自主 |
| 思迅 / 企迈 | 私有部署 + 抖音/美团/饿了么聚合；企迈 2000+ 连锁 | 全渠道聚合、连锁管控 | 信创适配、加盟分账、深度定制 |

**Reggie 能力现状评级（竞析）**：全渠道对接❌、多租户❌、会员私域❌、开放生态❌、AI/BI⚠️（仅基础报表）、硬件集成⚠️（无抽象层）、部署弹性❌（单体）、合规❌。

**差异化护城河（竞析结论）**：零许可费、数据自主可控、可深度二开、私有部署——精准命中"连锁数据自主 / 信创私有化 / 规避平台抽佣"三痛点。

### 2.3 竞争行动建议（按 ROI，竞析）
- **P0**：多租户 SaaS 化 + 连锁管控 + 加盟分账；全渠道外卖"四通"适配器（走开源透明不抽佣路线）。
- **P1**：AI/BI 模块化（销量预测/推荐/定价/排班）；会员私域基座（储值/积分/企微）。
- **P2**：开放 API + 插件/应用市场；硬件集成抽象层；云原生 + 信创适配 + 等保合规基线。

### 3.1 关键架构方案（摘要）
- **门店 / 品牌 / 不同合同关系（直营·加盟·租用·联营·代销）数据隔离（R-14/R-21）**：补全 `shopping_cart`/`dish_evaluation` 的 `tenant_id`（Flyway 迁移；`ai_provider_config` 经核验为系统级全局表，保留白名单、不补列），插件空上下文由 fail-closed 改 **fail-fast 抛 `TenantContextMissingException`**，确保自托管实例内多门店 / 连锁 / 租用租赁 / 联营代销等不同合同关系的数据安全隔离；层级模型 `tenant（品牌/连锁/合同主体）→ store（门店）→ user`，总部聚合看板，按合同类型分账在 tenant 层规则引擎计算。
- **全渠道适配层（R-15）**：统一 `UnifiedOrder` 模型 → 美团/饿了么/抖音适配器（接口+工厂+DB 配置，复用支付/AI 范式）→ 聚合接单 + 出餐状态回传；开源透明不抽佣，新增平台只实现统一接口。
- **持久化事件总线（R-13）**：Kafka/RabbitMQ（或 DB 轮询兜底，保 JDK8 兼容），订单/支付/通知发布事件、幂等消费、死信重试，先覆盖三大域解耦上帝类。
- **无状态会话与池治理（R-01/R-02/R-05）**：会话外置 Redis（Spring Session 或 Token→Redis）；限流 Lua 改旁路独立池；权限解析缓存 Redis（版本失效），去除类级 `@Transactional` 对只读路径污染。

### 4.4 里程碑可量化退出标准（摘要）
- **M1**：无状态鉴权全量上线；会话跨节点共享；租户 `tenant_id` 强校验拦截绕过；限流旁路化后 HTTP 线程零阻塞。

- **M3**：单实例多租户隔离可用（≥90% 表带 tenant_id）；连锁总部可建门店下发管控；四通框架 + 美团/饿了么端到端跑通。
- **M4**：加盟分账账期/规则闭环（不接真实资金通道）；四通全平台统一路由；调度分组 + 锁看门狗上线。
- **M5**：完成 1–2 个核心限界上下文拆分 + ACL；领域事件可落库重放；会员储值/积分骨架可用。
- **M6**：配置/SQL 版本化可回滚（Flyway）；**Spring Boot 退出 EOL（升 2.7.x LTS）**；会员私域可用。
- **M7**：AI/BI 模块上线；开放 API + 插件框架可用；文档漂移 CI 拦截。
- **M8**：硬件抽象层统一（KDS/打印/扫码/POS）；应用市场可上架/安装。
- **M9**：信创栈适配完成；等保合规基线达标；云原生弹性部署（多副本 + 配置外置）。

### 4.5 利益相关者沟通要点
- **高管视图**：①先地基后护城河，前期 18–23 人周对冲竞品最大短板"稳定性"；②P0 护城河命中 320 亿 SaaS 市场三痛点；③总投入 116–164 人周可控，前期仅占 ~15%；④踩中 AI 15%→50% 与私域复购红利；⑤风险前置收敛（分账/信创后置）。
- **工程视图**：①债务清单（Session 内存态、Redis8/DB20、上帝类、无CI、SB EOL、租户10表绕过）；②消债 M1–M2，M6 退出 EOL；③异步化+事件总线为 SaaS/四通提供扩展底座；④上帝类拆分跨 M5–M6 需 ACL 控回归；⑤JDK1.8 冻结约束升级。
- **设计/产品视图**：①出餐 KDS 慢 15–30% → 异步+并发后提速；②多平台日均 2h/错发 2.3%/费率 18–25% → 四通统一降错发降费；③C 端加载慢 43.2%/支付流失 34% → 无状态+缓存+异步降首屏；④私域复购 21%→40–70%、获客 52→8 元；⑤损耗 8–12% → AI 预测/排班优化备货。
