## 二、逐组件深度评估

### 2.1 【必须调整】Spring Boot 2.4.5 → Spring Boot 3.2+

| 维度 | 详情 |
|------|------|
| **当前状况** | Spring Boot 2.4.5，2021 年 5 月发布 |
| **问题严重度** | 🔴 高危 |
| **核心问题** | 1. 2.4.x 已于 2021 年停止免费维护，不再接收安全补丁<br>2. 无法享受 Virtual Threads（Java 21）带来的吞吐量质变<br>3. 与 Spring Cloud 2022+、Spring Security 6 完全不兼容<br>4. CVE 漏洞不再修复（如 CVE-2023-20860 等 Spring 框架级漏洞） |
| **瓶颈表现** | 当前 30+ Controller 的单体架构可支撑 ~1000 QPS，若要到 5000+ 必须升级 |
| **调整建议** | 升级至 **Spring Boot 3.2.x + JDK 17 LTS** |
| **预期收益** | • 安全补丁恢复（运维风险清零）<br>• GraalVM Native Image 编译选项（启动时间从 30s → 0.1s）<br>• 原生可观测性增强（Micrometer 深度集成）<br>• Record/Sealed/Pattern Matching 新语法糖，减少 30% 样板代码 |
| **迁移成本** | 约 5-8 人天 |
| **对现有系统影响** | ⚠️ 中等 — `javax.*` → `jakarta.*` 全局包名替换；Spring Security 6 配置 API 变更；需全量回归测试 |
| **迁移步骤** | 1. `javax.*` → `jakarta.*` 全局替换<br>2. Spring Security 配置类改为 Lambda DSL<br>3. `spring.factories` → `META-INF/spring/auto-configuration.imports`<br>4. MyBatis Plus 同步升级至 3.5.5+<br>5. SpringDoc 升级至 2.x（Jakarta 兼容） |

### 2.2 【必须调整】MySQL 5.7 → MySQL 8.0

| 维度 | 详情 |
|------|------|
| **当前状况** | MySQL 5.7 |
| **问题严重度** | 🔴 高危 |
| **核心问题** | 1. 官方 Extended Support 已于 2023 年 10 月终止<br>2. 缺少以下关键能力：窗口函数、CTE（WITH RECURSIVE）、JSON 类型增强、不可见索引、原子 DDL<br>3. 认证插件 `mysql_native_password` 已废弃，安全等级低<br>4. GROUP BY 宽松模式隐藏数据问题 |
| **瓶颈表现** | 数据分析类查询（如经营报表环比/同比）需在 Java 层做大量聚合计算，SQL 层无法利用窗口函数简化 |
| **调整建议** | 升级至 **MySQL 8.0 LTS** |
| **预期收益** | • 窗口函数 → 近7日趋势、环比、同比等查询代码量减少 60%<br>• CTE → 树形分类查询不再需要递归代码<br>• JSON 类型 → 订单扩展属性/菜品口味等灵活存储<br>• 不可见索引 → 安全删索引，零停服优化<br>• 降序索引 → 列表排序查询快 20-50% |
| **迁移成本** | 约 2-3 人天 |
| **对现有系统影响** | ⚠️ 中低 — GROUP BY 严格模式可能导致部分 SQL 报错（需检查修正）；认证插件需调整 JDBC 连接串；保留字冲突需检查（rank/lead/lag/system 等） |
| **迁移步骤** | 1. 升级前执行 `mysqlcheck` 检查表兼容性<br>2. 修改 JDBC URL 中的认证方式<br>3. 开启 `sql_mode` 严格模式，修正不合规 SQL<br>4. 全量回归测试所有查询接口 |

### 2.3 【必须调整】Druid 1.1.23 → HikariCP（已内置）

| 维度 | 详情 |
|------|------|
| **当前状况** | Druid 1.1.23（2019 年发布） |
| **问题严重度** | 🔴 高危 |
| **核心问题** | 1. 版本 1.1.23 存在已知安全漏洞（CVE-2021-43797 等）<br>2. 性能较 HikariCP 低 30-50%（HikariCP 是 Spring Boot 2.x 默认连接池）<br>3. Druid 的 SQL 监控功能在当前项目中几乎未使用<br>4. 引入额外依赖，增加攻击面 |
| **调整建议** | 移除 Druid，切换至 **HikariCP**（Spring Boot 内置，零额外依赖） |
| **预期收益** | • 减少安全攻击面（消除 CVE 风险）<br>• 连接池性能提升 ~40%<br>• 减少维护一个第三方依赖<br>• 配置更简洁（Spring Boot 原生配置属性） |
| **迁移成本** | 约 0.5 人天 |
| **对现有系统影响** | 🟢 低 — 仅需移除 `pom.xml` 中的 Druid starter 和 `application.yml` 中 Druid 专属配置，Spring Boot 自动切换至 HikariCP |

### 2.4 【必须调整】前端：Vue 2 裸写 → Vue 3 + Vite 工程化

| 维度 | 详情 |
|------|------|
| **当前状况** | Vue 2 CDN 引入 + Element UI + jQuery，无构建工具，HTML 文件直接嵌入 `<script>` 标签 |
| **问题严重度** | 🔴 高危 |
| **核心问题** | 1. Vue 2 已于 2023 年 12 月 EOL<br>2. Element UI 绑死 Vue 2，不再维护<br>3. 无构建工具 = 无 Tree-shaking（全量加载 Element UI ~600KB）<br>4. 无模块化 = 所有 JS 塞在一个文件（index.js 单文件过大）<br>5. 无 TypeScript 支持<br>6. 开发体验差（无 HMR 热更新，改代码需手动刷新）<br>7. jQuery 与 Vue 混合使用，DOM 操作冲突风险 |
| **瓶颈表现** | 当前前端加载 Element UI 全量（~600KB）+ 自定义 JS（~200KB），首屏白屏时间 3-5s；新增页面直接追加到 index.html，文件持续膨胀 |
| **调整建议** | **渐进式迁移**：Phase 1 组件化重构（不改框架）→ Phase 2 切 Vue 3 + Element Plus + Vite |
| **预期收益** | • 首屏加载从 ~800KB → ~200KB（Tree-shaking + 按需加载）<br>• 开发热更新 <1s（Vite HMR）<br>• TypeScript 类型安全，减少 40% 运行时错误<br>• 组件复用度从 ~10% → ~60%<br>• Composition API 解决 mixin 命名冲突问题 |
| **迁移成本** | 约 15-20 人天（全量迁移）<br>Phase 1 组件化：3-5 人天（不换框架）<br>Phase 2 迁移 Vue 3：10-15 人天 |
| **对现有系统影响** | ⚠️ 中等 — 建议分两个 Phase：<br>Phase 1（立即）：不改框架，仅做页面组件化拆分（提取公共组件）<br>Phase 2（v3.0 发布后）：完整迁移至 Vue 3 + Vite 独立项目 |
| **迁移策略** | Phase 1：提取 SearchBar/DataTable/FormDialog/StatCard 等通用组件<br>Phase 2：新建独立 Vue 3 项目 → 逐页迁移 → 最后切路由 |

### 2.5 【建议调整】Redis 单机 → Redis Sentinel/Cluster

| 维度 | 详情 |
|------|------|
| **当前状况** | Redis 单机部署，仅用于 Session + 验证码存储 |
| **问题严重度** | 🟡 中等（商户量 < 50 时不急） |
| **核心问题** | 1. 单点故障：Redis 宕机 → 所有用户 Session 丢失 → 全量重新登录<br>2. 验证码丢失 → 登录流程中断<br>3. 缓存利用率极低（仅做 Session/验证码），未发挥应有价值 |
| **调整建议** | Phase 1：引入 **Redisson** 做分布式锁 + 菜品/分类/配置缓存<br>Phase 2：Redis Sentinel（主从 + 自动故障转移） |
| **预期收益** | • 消除单点故障（Session 持久化）<br>• 菜品列表缓存命中率可达 90%+，数据库查询减少 50%+<br>• Redisson 分布式锁替代 synchronized，支持多实例部署 |
| **迁移成本** | Phase 1：2 人天<br>Phase 2：1 人天 |
| **对现有系统影响** | 🟢 低 — API 完全兼容，仅增加 Redisson 依赖和配置 |

### 2.6 【建议调整】本地文件存储 → MinIO 对象存储

| 维度 | 详情 |
|------|------|
| **当前状况** | 菜品/套餐图片存于 `uploads/` 本地目录 |
| **问题严重度** | 🟡 中等 |
| **核心问题** | 1. 无法水平扩展：多实例部署时，图片只存在于某一台服务器<br>2. 无 CDN 加速：用户端加载图片慢<br>3. 备份困难：需同步本地目录<br>4. 磁盘空间不可控增长 |
| **调整建议** | Phase 1 引入 **MinIO**（自建对象存储） |
| **预期收益** | • 多实例共享文件（无状态化，可横向扩展）<br>• 图片上传后自动生成缩略图（MinIO 事件通知）<br>• 断点续传、分片上传支持<br>• 后续可无缝迁移至阿里云 OSS（S3 兼容 API） |
| **迁移成本** | 约 2 人天 |
| **对现有系统影响** | 🟢 低 — 修改 `CommonController` 的文件上传/访问逻辑，增加 MinIO Client，存量图片一次性迁移 |

### 2.7 【Phase 2 引入】消息队列 RabbitMQ

| 维度 | 详情 |
|------|------|
| **当前状况** | 无消息队列，异步任务（短信、数据预聚合）直接在线程中执行 |
| **问题严重度** | 🟡 中等（当前阶段影响不大） |
| **核心问题** | 1. 短信发送阻塞 HTTP 请求线程（阿里云 SMS API 调用 ~1-3s）<br>2. WebSocket 集群场景需消息广播（单机 STOMP 无法跨实例）<br>3. 大数据量报表生成无法异步处理<br>4. 无分布式事务补偿机制 |
| **调整建议** | Phase 2 引入 **RabbitMQ 3.12+** |
| **预期收益** | • 短信/通知异步化，接口响应时间降低 30-50%<br>• WebSocket 消息跨实例广播（支撑多实例部署）<br>• 订单状态变更可靠通知（消息持久化，不丢单）<br>• 为后续分布式事务（订单-库存-支付）提供基础设施 |
| **迁移成本** | 约 3 人天 |
| **对现有系统影响** | 🟢 低 — 新增独立模块，不影响现有代码 |
| **为什么不立即引入？** | 当前单机部署 + 无 WebSocket 集群 + 短信量小的阶段，MQ 是过度设计。Phase 2（多实例 + WebSocket 集群）时再引入性价比最高 |

## 五、不做调整的组件及原因

| 组件 | 不调整原因 |
|------|-----------|
| Maven | 标准构建工具，团队熟悉，无替代必要。Gradle 仅在有 Kotlin 需求时考虑 |
| MyBatis Plus | 项目深度使用 LambdaQueryWrapper，换 JPA 成本巨大且无收益。升级版本即可 |
| Jasypt | 当前阶段够用。多环境+多团队协作场景再考虑 Vault |
| SpringDoc OpenAPI | 已正确选型，无需更换。Spring Boot 3 升级后同步升至 2.x |
| H2 (Test) | 测试数据库 OK，不需要调整 |
| Lombok | 虽 Java 14+ 有 Record，但大量 Entity 使用 Lombok。逐步迁移 |

## 六、风险与回滚预案

| 调整项 | 风险 | 回滚方案 |
|--------|------|---------|
| JDK 17 升级 | 第三方 JAR 不兼容 | 保留 JDK 8 环境，Maven `<java.version>` 切回 8 即可 |
| Spring Boot 3 | `javax.*` 遗漏导致编译失败 | Git 分支隔离，`feature/sb3-upgrade` 分支验证通过后再合入 master |
| MySQL 8.0 | GROUP BY 问题导致查询报错 | mysqldump 全量备份，出问题立即恢复 5.7 |
| Druid 移除 | 无（Spring Boot 自动切换 HikariCP） | 重新引入 Druid starter 依赖即可 |
| MinIO 迁移 | 存量图片迁移遗漏 | 保留本地 uploads/ 目录作冗余备份一个月 |

## 七、总结

### 一句话结论

当前技术栈的**后端核心（Spring Boot、JDK、MySQL、Druid）均处于 EOL/有漏洞状态，存在实质性的运维安全风险**，必须在本月内完成 Phase 1 升级；前端的 Vue 2 裸写模式虽不影响安全，但严重拖累开发效率和用户体验，建议在 Phase 2 完成工程化改造。
