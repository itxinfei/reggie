# 瑞吉外卖 三角色（顾客 / 管理员 / 骑手）体验修复计划

> 制定日期：2026-09-28
> 适用范围：顾客端（`/front`）、管理后台（`/backend`）、骑手端（`/rider`）及对应后端模块
> 文档性质：修复实施总纲，按阶段交付，不修改任何线上配置

---

## 1. 修复目标

### 1.1 总体目标
将"顾客—商家—骑手"三方协作链路补齐为**可用、可信、连贯**的产品闭环，消除上一轮审查中识别的体验断点与功能缺失。

### 1.2 分角色目标
- **顾客端**：核心下单链路零断头路；补齐自提 / 排队取号 / 到店预订；支付、会员、积分、发票形成完整闭环。
- **管理后台**：菜单与权限按角色精确收敛；订单—库存—成本数据贯通；消除重复与无入口页面。
- **骑手端**：从"只能接单配送"升级为"可结算、可评价、可申诉、可接收通知"的合格工作端。

### 1.3 质量目标
- 三端同一订单状态文案 100% 一致，无悬挂订单（已送达却永不完成）。
- 骑手知情权、收入可见性、异常出口 100% 覆盖。
- 关键流程（下单 / 接单 / 配送 / 退款）端到端回归通过率 100%。

## 2. 修复范围

### 2.1 范围内（In Scope）
| 域 | 内容 |
|---|---|
| 跨端地基 | 订单状态机统一、自动完成规则、实时通知底座 |
| 骑手端 | 我的收入 / 评价查看 / 异常上报 / 转单改派 / 消息中心 / 取餐码 / 接单上限 / 登录态 / 号码保护 |
| 顾客端 | 到店自提 / 排队取号 / 到店预订 / 待付款直达支付 / 会员充值线上化 / 积分出口 / 评价骑手 / 领券入口 / 地图降级 / 我的足迹 |
| 管理后台 | 菜单按角色过滤 / 员工角色字段 / 自营拒单 / 库存扣减明细 / 报表合并 / 打印菜单归位 / 发票上传链路 / 大屏主动告警 |
| 后端能力 | 骑手结算、骑手评分、异常工单、消息推送、履约方式枚举、虚拟号接口（新领域模型与接口） |

### 2.2 范围外（Out of Scope）
- 业务表结构 / 配置的破坏性变更（仅新增模型与字段，不改动既有核心表语义）。
- 外卖平台（美团 / 饿了么）对接协议的改造。
- 基础设施（数据库、Redis、服务器）扩容与运维。
- AI 推荐与 AI 客服的能力升级（仅做与三端体验的衔接对齐）。

## 3. 优先级划分

| 优先级 | 定义 | 对应内容 |
|---|---|---|
| **P0（阻断级）** | 影响核心闭环，不修则产品不可用 | 状态机统一、自动完成、通知底座、骑手收入/评价/异常/消息/取餐码 |
| **P1（重要级）** | 明显拉低体验，需在第二个版本内完成 | 后台权限过滤、自提/排队/预订、支付直达、会员/积分闭环、自营拒单、库存联动、接单上限 |
| **P2（打磨级）** | 不阻塞使用，属于体验与整洁度 | 报表合并、登录态、号码保护、足迹、发票上传、大屏告警、死角清理 |

> 优先级与审查报告中的 C / A / R 问题编号一一对应，详见第 4 节时间表附带的对照表。

## 4. 时间安排

> 以下为建议节奏（基于小团队 1 后端 + 1 前端 + 1 测试的配置估算）。实际可按资源伸缩。

### 阶段 3：P2 打磨（第 11–13 周）

## 6. 验证标准（每阶段）

| 阶段 | 验证标准 |
|---|---|
| M0 地基 | 同一订单在三端展示的状态文案完全一致；通知接口可分别向顾客/骑手/后台推送；超时与自动完成规则单测通过 |
| M1 骑手 | 骑手可见每单配送费与日/周收入；可见服务分与评价；可提交异常并转单；收到派单/催单提醒；取餐需核销 |
| M2 体验 | 顾客可自提/排队/预订；待付款直达支付；会员可线上充值；积分可兑换；后台不同角色菜单不同；库存扣减可见 |
| M3 打磨 | 报表不重复；无死角页面；骑手可记住登录与自助找回；双向号码保护；发票可上传票面 |

**通用验收红线**
- 不引入 JDK 9+ 语法、不破坏既有 Swagger/接口契约。
- 所有新增接口通过参数校验与异常捕获（遵循项目安全规范）。
- 既有 742 个单测与端到端用例 100% 通过（或显式标注预期变更）。

## 7. 风险控制措施

| 风险 | 等级 | 控制措施 |
|---|---|---|
| 状态机重构波及既有流程 | 高 | 先在 M0 做**纯映射层**，三端只读新枚举，旧状态保留兼容；灰度开关逐步切换 |
| 实时通知引入推送网关，增加外部依赖 | 中 | 通知底座设计降级：推送不可用时回退轮询，保证功能不中断 |
| 新增领域模型（结算/评分/工单）改动数据库 | 中 | 仅新增表/字段；提供参考迁移脚本与测试 schema 同步；DBA 评审后上线 |
| 骑手端改动影响线上配送 | 高 | P0 骑手端先在测试环境跑完整接单—送达—结算链路，再灰度小流量 |
| 后台菜单按角色过滤误伤权限 | 中 | 权限树以"白名单"方式逐步开放，旧角色默认保留原有可见范围 |
| 配置类改动（高德 Key、推送证书）泄露 | 中 | 严禁写入代码库；走环境变量 / 配置中心；纳入 `.gitignore` 既有机制 |
| 范围蔓延（顺手改无关功能） | 低 | 严格按本计划阶段范围执行，超出项登记为独立需求 |

## 8. 修复完成后的验收方式

1. **功能验收（UAT）**：产品按第 6 节标准逐条走查三端，签署验收单。
2. **端到端链路验收**：用自动化套件（项目 `tests/` 下的 Playwright 链路）跑通：
   - 顾客下单 → 商家接单 → 骑手接单/取餐/送达 → 顾客确认/自动完成 → 评价骑手 → 骑手收入入账。
   - 异常分支：顾客取消（各阶段）、退款、催单触达、超时自动取消。
3. **状态一致性验收**：脚本比对三端同一订单状态字段，断言无偏差。
4. **性能验收**：通知触达时延 < 3s；首页与列表页首屏 < 1.5s（既有基线）。
5. **回归验收**：全量单测 + 既有 E2E 套件通过，覆盖率不低于当前基线。

## 9. 后续预防方案

### 9.1 设计期预防
- 新增任何跨端状态，必须先登记到**统一状态枚举文档**，禁止各端自造文案。
- 任一新端（如未来新增"商家 App"）接入订单，必须复用同一状态机与通知底座。

### 9.2 开发期预防
- 骑手端、顾客端、后台的新功能须通过"三角色走查清单"评审（覆盖：该角色能否看见自己的收入/评价/异常/通知）。
- 代码评审（Code Review）加入"是否引入新死角页面 / 无入口功能"检查项。

### 9.3 测试期预防
- 将三端状态一致性校验固化为**持续集成断言**，防止回归。
- 每版本保留"三角色体验回归用例集"，纳入发布门禁。

### 9.4 运营期预防
- 上线后建立**三角色满意度轻量反馈**（顾客评分、骑手端 NPS、后台易用性问卷），季度复盘。
- 配置类依赖（地图 Key、推送证书）设置到期提醒与失效监控，避免"默认降级"长期无人发现。
