# 瑞吉外卖系统 — 业务功能差距分析报告（修订版）

> 基准日期：2026-08-10（v2 修订）
> 分析范围：全量后端 Service/Controller/Entity/SQL，对标美团商家版、饿了么商家版、客如云、二维火、哗啦啦、天财商龙、美味不用等

## 一、项目现状概览

### 1.1 技术架构

| 维度 | 现状 |
|---|---|
| 后端 | Spring Boot 2.4.5 + MyBatis-Plus 3.4.2 + Java 8 |
| 数据库 | MySQL 8.x，61 张业务表，48,000 行 SQL（含 4.4 万条行政区划数据） |
| 前端管理台 | Vue 2 + Element UI，传统 HTML 多页面 |
| 前端用户端 | Vant.js 移动端，传统 HTML 多页面 |
| 缓存 | Redis（幂等锁、缓存） |
| 多租户 | tenant_id 字段级隔离 |

### 1.3 订单状态机

```
PENDING_PAYMENT(1, 待付款)
    ↓ 支付成功
ORDERED(2, 待接单)
    ↓ 接单
DELIVERING(3, 配送中)
    ↓ 完成/取消/退款
COMPLETED(4, 已完成) / CANCELLED(5, 已取消) / REFUNDED(6, 已退款)
```

### 1.4 订单来源类型

| 类型 | 说明 |
|---|---|
| TAKEOUT | 外卖配送 |
| EAT_IN | 堂食扫码 |
| QUEUE | 排队取号 |
| RESERVATION | 预订到店 |

## 二、功能实现深度评估（含勘误）

> 以下评估基于逐行代码审查，已修正初版中的不准确描述。

### 2.1 订单模块

| 功能点 | 实现深度 | 说明 |
|---|---|---|
| 外卖下单 | ★★★★☆ | 完整流程：购物车→地址校验→金额计算→幂等锁(Redis SETNX)→落库→扣库存→清购物车→触发打印 |
| 堂食下单 | ★★★★☆ | 直接传菜品列表→服务端价格校验→桌台校验→落库→扣库存→触发打印 |
| 订单备注 | ★★★☆☆ | **Orders 表有 remark 字段**（`@Schema(description="备注", example="少放辣")`），支持整单备注；但 OrderDetail 无备注字段，不支持逐菜品备注 |
| 状态流转 | ★★★★☆ | 6 种状态 + 状态机校验，含已退款(6)状态 |
| 幂等保护 | ★★★★★ | Redis SETNX + 数据库 idempotency_key 双重保障 |
| 再下单 | ★★★☆☆ | 查询历史订单明细→重建购物车，缺少"部分菜品已下架"的处理 |
| 订单统计 | ★★★☆☆ | 按状态统计数量和金额，缺少趋势对比 |
| 超时自动取消 | ★★★★☆ | 定时任务扫描超时订单，自动取消 + 回退库存 |

**实际缺失项：**
- 无逐菜品备注（"这份不要辣，那份多放醋"）
- 无预计送达时间自动计算
- 无订单取消后的退款流程联动（取消≠退款，需分开处理）
- 无配送费计算
- 无小费/打赏功能
- 无订单分享（多人拼单）
- 无堂食分批出餐（先上凉菜后上热菜）

### 2.2 菜品模块

| 功能点 | 实现深度 | 说明 |

| 菜品 CRUD | ★★★★★ | 完整，含名称、价格、图片、描述、分类、排序、商品码 |
| 口味管理 | ★★★★☆ | **name-value 结构化**（如 name="辣度", value="微辣"），比纯文本好，但缺少预设选项库 |
| 上下架 | ★★★★☆ | 支持批量上下架 |
| 库存管理 | ★★★★☆ | stock_qty + min_stock，下单扣减 + 补充 + 自动售罄 |
| 菜品统计 | ★★★☆☆ | 基本统计 |

**实际缺失项：**
- 无规格管理（大份/中份/小份，不同价格）
- 无菜品多图（当前只有单张 image 字段）
- 无菜品视频
- 无菜品配料表（BOM）— 核心缺失
- 无菜品制作时间预估
- 无菜品热度权重（影响排序和推荐）
- 无菜品标签（"辣"、"素食"、"招牌"、"新品"）
- 无菜品起售数量（部分菜品要求最少点 N 份）

## 三、对标竞品差距分析

### 3.1 对标维度说明

| 竞品 | 定位 | 核心优势 |
|---|---|---|
| 美团商家版 | 外卖平台商家管理 | 平台对接深度、数据分析、营销工具 |
| 饿了么商家版 | 外卖平台商家管理 | 平台对接、会员体系 |
| 客如云 | 餐饮 SaaS POS | 硬件+软件一体化、供应链、多门店 |
| 二维火 | 餐饮收银系统 | 扫码点餐、供应链、会员营销 |
| 哗啦啦 | 餐饮 SaaS | 供应链金融、多业态、全渠道 |
| 天财商龙 | 餐饮管理 | 会员营销、供应链、数据中台 |
| 美味不用等 | 排队预约 | 排队等位、预约、智能叫号 |

### 3.2 差距矩阵

#### 🔴 P0 — 核心业务断层（必须补齐）

| # | 功能 | 当前状态 | 竞品对标 | 差距描述 | 实用价值 |
|---|---|---|---|---|---|
| 1 | **菜品-食材 BOM 配方** | 不存在 | 客如云/哗啦啦 | 没有"一道菜需要哪些食材、多少量"的关联，成本无法核算、库存无法自动扣减 | ⭐⭐⭐⭐⭐ 经营核心 |
| 2 | **下单自动扣食材库存** | 不存在 | 客如云/二维火 | 菜品库存扣的是一个抽象数字，不是真实食材消耗 | ⭐⭐⭐⭐⭐ 防超卖 |
| 3 | **食材成本 → 菜品成本 → 毛利率** | 不存在 | 所有竞品 | 经营者无法知道每个菜品赚多少钱 | ⭐⭐⭐⭐⭐ 定价依据 |
| 4 | **厨房显示系统 (KDS)** | 不存在 | 客如云/二维火 | 后厨没有待制作订单列表，无法高效出餐 | ⭐⭐⭐⭐⭐ 堂食效率 |
| 5 | **现金收款** | 不存在 | 所有竞品 | 堂食场景必须支持现金 | ⭐⭐⭐⭐⭐ 基本支付 |
| 6 | **储值卡/会员余额支付** | 不存在 | 客如云/哗啦啦 | 会员储值是餐饮 SaaS 的核心营收模式 | ⭐⭐⭐⭐⭐ 锁客 |
| 7 | **优惠券使用规则引擎** | 只有模板+领取 | 所有竞品 | 无法设置"满 X 减 Y"、"指定菜品可用"、"每人限领"等规则 | ⭐⭐⭐⭐⭐ 营销基础 |
| 8 | **菜品规格** | 只有口味文本 | 二维火/客如云 | 无法区分大/中/小份及不同价格 | ⭐⭐⭐⭐ 售价灵活 |
| 9 | **外卖平台真实对接** | 空壳 | 美团/饿了么核心 | 无法从美团/饿了么接单 | ⭐⭐⭐⭐ 渠道营收 |

## 五、实施路径建议

### 阶段划分原则

1. **业务闭环优先**：先补齐"从点单到出餐到结账"的完整链路
2. **营收能力优先**：先补齐能直接带来收入的功能
3. **依赖关系**：BOM 配方是成本核算和库存自动化的前提
4. **最小可用**：每个阶段产出可独立使用的功能，不依赖后续阶段

### 阶段 1：成本闭环 + 基础收银（预计 4-5 周）

> 目标：让经营者知道"每道菜赚多少钱"，并支持堂食现金结账

```
1.1 菜品-食材 BOM 配方
    ├── 新建 dish_ingredient 表
    ├── DishService 增加 getIngredients / saveIngredients
    ├── DishController 增加 BOM 相关接口
    └── 前端菜品编辑页增加"配方"Tab

1.2 下单自动扣食材库存
    ├── OrderServiceImpl.submit() 中增加 deductIngredientStock()
    ├── 库存不足时提示（非阻断）
    ├── 取消/退款时回退食材库存
    └── 库存不足自动停售菜品

1.3 成本核算与毛利率
    ├── DishService 增加 getCostPrice()（根据 BOM 计算）
    ├── DishService 增加 getProfitRate()
    ├── ReportService 增加 getCostReport()
    └── Dashboard 增加毛利率展示

1.4 现金收款
    ├── Orders 表 pay_method 增加 3=现金
    ├── 堂食结账接口支持现金
    └── 收银台界面

1.5 日结/交班
    ├── 新建 daily_settlement + settlement_detail 表
    ├── SettlementService：生成日结报表（按支付方式汇总）
    ├── 交班打印（现金/微信/支付宝/储值卡各多少）
    └── 日结历史查询
```
