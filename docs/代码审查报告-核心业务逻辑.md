# 瑞吉外卖项目 — 核心业务逻辑审查报告

> **审查范围**：订单、购物车、支付、权限安全、员工登录、Dashboard、菜品/套餐管理、评价、库存、会员等核心模块  
> **审查时间**：2026-07-14  
> **审查工具**：代码静态阅读 + 架构分析  

---

## 一、总体评价

| 维度 | 评分 | 说明 |
|------|------|------|
| 架构清晰度 | ⭐⭐⭐⭐ | 分层合理（Controller → Service → Mapper），职责分明 |
| 安全性 | ⭐⭐⭐ | 有 BCrypt、防暴力破解、权限切面，但存在若干安全隐患 |
| 并发安全 | ⭐⭐⭐ | 乐观锁扣库存做得不错，但购物车减一、幂等令牌仍有竞态风险 |
| 事务管理 | ⭐⭐⭐⭐ | 核心操作均加了 `@Transactional`，缓存双删策略合理 |
| 可维护性 | ⭐⭐⭐ | 代码量大（159个文件），部分 Service 方法较长 |

## 二、逐模块详细审查

### 2.1 订单核心逻辑（OrderServiceImpl）

#### ✅ 优点
1. **幂等性保护**：通过 `idempotencyKey` 防止重复下单，Controller 层做了前置校验
2. **乐观锁扣库存**：`deductStockAtomic` 使用 `WHERE stock_qty >= ?` 防止超卖
3. **套餐库存联动扣减**：正确遍历 `SetmealDish` 并乘以 `copies` 系数
4. **堂食扫码下单**：独立于购物车流程，直接服务端验价防篡改
5. **租户隔离**：所有查询均带 `tenantId` 过滤
6. **用户信息回填**：`backfillUserInfoBatch` 批量查询避免 N+1

#### ⚠️ 问题与建议

| # | 严重度 | 问题描述 | 位置 | 建议 |
|---|--------|----------|------|------|
| 1 | 🔴 高 | **购物车减一存在竞态条件**：`sub()` 先 `getOne` 再 `update`，两次操作非原子。高并发下可能出现负数 | ShoppingCartServiceImpl.java:43-48 | 改为类似库存扣减的原子操作：`UPDATE shopping_cart SET number = number - 1 WHERE id = ? AND number > 1` |
| 2 | 🟡 中 | **幂等令牌生成方式不安全**：`userId_timestamp_random6` 中 random 使用 `Math.random()`（非线程安全），且时间戳精度不够 | OrderServiceImpl.java:643 | 改用 `UUID.randomUUID().toString()` 或雪花算法 |
| 3 | 🟡 中 | **扣库存 SQL 拼接有注入风险**：`setSql("stock_qty = stock_qty - " + qty.toPlainString())` 虽然 qty 是 BigDecimal，但拼接方式不优雅 | OrderServiceImpl.java:284 | 使用 MyBatis-Plus 的 `UpdateWrapper.set()` 方法 |
| 4 | 🟢 低 | **取消订单未回退库存**：用户取消订单后，已扣减的库存不会返还 | OrderServiceImpl.java:412-426 | 建议在 `cancelOrder` 中增加库存回退逻辑 |
| 5 | 🟢 低 | **拒单也未回退库存**：同上 | OrderServiceImpl.java:392-402 | 同上 |
| 6 | 🟢 低 | **订单状态常量魔法值**：`Orders.STATUS_ORDERED` 等散落在各处 | 多处 | 建议统一使用枚举类 `OrderStatus` |
| 7 | 🟡 中 | **`userPage` 返回类型不统一**：返回 `Page<?>` 而非 `Page<OrderDto>`，调用方需要强制转换 | OrderServiceImpl.java:336 | 改为泛型 `Page<OrderDto>` |

### 2.2 购物车逻辑（ShoppingCartServiceImpl）

#### ✅ 优点
- 减一操作有乐观锁保护（`gt(number, 1)` 条件）
- 数量为 1 时自动删除，逻辑清晰

#### ⚠️ 问题

| # | 严重度 | 问题描述 | 建议 |
|---|--------|----------|------|
| 1 | 🔴 高 | **`sub()` 方法不是原子操作**：先 `getOne` 查数量，再 `update` 减 1。两个请求同时读到 `number=2`，都减 1 后变成 1（应为 0） | 改为纯 SQL 原子更新：`UPDATE shopping_cart SET number = number - 1 WHERE id = ? AND number > 1` |
| 2 | 🟡 中 | **没有并发加购保护**：如果两个请求同时往购物车添加同一菜品，可能创建重复记录 | 加购时使用 `ON DUPLICATE KEY UPDATE` 或唯一索引 `(user_id, dish_id/setmeal_id)` |

### 2.3 支付逻辑

#### ⚠️ 问题

| # | 严重度 | 问题描述 | 建议 |
|---|--------|----------|------|
| 1 | 🔴 高 | **未发现支付回调处理逻辑**：代码中只有 `PayRequestDTO`，但没有微信支付/支付宝的异步回调 Controller | 需要补充支付回调接口，处理支付结果通知 |
| 2 | 🟡 中 | **订单金额由前端传入购物车 `amount` 字段**：下单时总金额是 `item.getAmount() * item.getNumber()` 累加，但 `amount` 来自购物车，而购物车金额可能在商品调价后已过时 | 下单时应从 Dish/Setmeal 表重新查询最新价格 |
| 3 | 🟢 低 | **支付方式硬编码**：`payMethod` 只有 1=微信、2=支付宝，扩展性差 | 建议使用枚举 `PayMethod` |

### 2.4 权限与安全

#### ✅ 优点
1. **LoginCheckFilter**：统一拦截，支持 session 登录态校验
2. **PermissionAspect**：AOP 切面实现细粒度权限控制，支持 Redis 缓存权限
3. **BruteForceProtectionFilter**：基于 Redis + Lua 脚本的防暴力破解，支持 IP + 用户名双重维度
4. **CSRF Token 工具类**：有 `CsrfTokenUtil` 防护 CSRF 攻击

#### ⚠️ 问题

| # | 严重度 | 问题描述 | 位置 | 建议 |
|---|--------|----------|------|------|
| 1 | 🔴 高 | **LoginCheckFilter 中 EXCLUDE_URLS 重复定义**：`EXCLUDE_URLS` 数组和 `doFilter` 方法内的 `urls` 数组完全一样，维护两份 | LoginCheckFilter.java:45-66 + 69-90 | 删除 `doFilter` 内的 `urls` 局部变量，统一使用 `EXCLUDE_URLS` |
| 2 | 🟡 中 | **Session 固定攻击风险**：登录成功后没有新建 Session（`request.changeSessionId()`） | EmployeeController.java + UserController.java | 登录后调用 `request.changeSessionId()` 防止 Session Fixation |
| 3 | 🟡 中 | **Swagger 文档在生产环境暴露**：`/swagger-ui/**` 在 EXCLUDE_URLS 中放行，生产环境不应暴露 API 文档 | LoginCheckFilter.java | 通过 `@Profile("!prod")` 控制 Swagger 仅在开发环境启用 |
| 4 | 🟢 低 | **BaseContext 线程安全问题**：异步线程（如打印服务）中 `BaseContext` 的 ThreadLocal 值不会传递 | OrderServiceImpl.java:198-205 | 在 `AsyncConfig` 中配置 `TaskDecorator` 传递 ThreadLocal 上下文 |
| 5 | 🟢 低 | **权限切面无缓存穿透保护**：空权限集合也写入 Redis，但 TTL 较短（1小时），期间频繁查库 | PermissionAspect.java:124 | 考虑使用 Bloom Filter 或延长空集合缓存时间 |

### 2.5 员工登录与安全（EmployeeController）

#### ✅ 优点
1. **BCrypt 密码加密**：新密码使用 BCrypt，旧系统 MD5 自动升级
2. **密码自动升级机制**：`upgradeIfNeeded` 在每次登录时自动将 MD5 升级为 BCrypt
3. **账号禁用检查**：登录时校验 `status` 字段
4. **防暴力破解**：5次失败锁定15分钟

#### ⚠️ 问题

| # | 严重度 | 问题描述 | 建议 |
|---|--------|----------|------|
| 1 | 🟡 中 | **MD5 仍被允许使用**：`SecurityConstants.PASSWORD_TYPE_MD5` 支持旧密码，但不应鼓励继续使用 | 设置迁移期限，到期后强制要求修改密码 |
| 2 | 🟡 中 | **初始密码明文返回**：新增员工后返回明文初始密码到前端 | `EmployeeController.java:235` | 初始密码应通过短信/邮件发送，不在接口返回 |
| 3 | 🟢 低 | **忘记密码接口验证码存 Session**：短信验证码存储在 HttpSession 中，集群部署时会有问题 | `EmployeeController.java:175` | 改用 Redis 存储验证码 |
| 4 | 🟢 低 | **`isAdmin` 方法每次查询数据库**：每次权限校验都 `employeeService.getById(empId)` | `EmployeeController.java:368` | 可加入缓存或从 Session 中读取角色信息 |

### 2.6 Dashboard 统计逻辑（DashboardServiceImpl）

#### ✅ 优点
1. **多级缓存策略**：Redis Hash/ZSet/String 混合使用，TTL 分级合理
2. **优雅降级**：Redis 不可用时自动回退 MySQL 查询
3. **Pipeline 批量写入**：热销菜品使用 Pipeline 减少网络往返
4. **原子 RENAME**：使用 tempKey + rename 避免脏读
5. **租户隔离**：`tenantId == null` 时不使用缓存，防止超级管理员视图串数据

#### ⚠️ 问题

| # | 严重度 | 问题描述 | 建议 |
|---|--------|----------|------|
| 1 | 🟡 中 | **概览数据计算效率低**：`computeOverview` 一次查出今日所有订单再在 Java 层遍历 | 改为 SQL 聚合查询：`SELECT COUNT(*), SUM(amount), COUNT(CASE WHEN status=...) FROM orders WHERE ...` |
| 2 | 🟡 中 | **趋势数据同理**：`computeTrend` 全量查询后 Java 分组 | 使用 `GROUP BY DATE(order_time)` 在 SQL 层聚合 |
| 3 | 🟢 低 | **缓存 TTL 偏长**：热销菜品 15 分钟，高流量场景数据可能滞后 | 订单创建/状态变更时主动清除对应缓存（已在做） |

### 2.7 菜品/套餐管理（DishServiceImpl / SetmealServiceImpl）

#### ✅ 优点
1. **事务 + 缓存双删**：`saveWithFlavor`、`updateWithFlavor` 等都在事务提交后清除缓存
2. **套餐引用校验**：删除菜品前检查是否被套餐引用
3. **`@Cacheable(sync=true)`**：防止缓存击穿

#### ⚠️ 问题

| # | 严重度 | 问题描述 | 建议 |
|---|--------|----------|------|
| 1 | 🟡 中 | **`doubleDeleteAllEntries` 性能问题**：删除菜品/套餐缓存时使用 `KEYS pattern` 扫描，数据量大时阻塞 Redis | 改用 `SCAN` 命令（已在 `RedisCacheUtil` 中使用，但 `doubleDeleteAllEntries` 调用处可能触发大量 Key 删除） |
| 2 | 🟢 低 | **菜品状态切换与库存耦合**：`autoToggleSoldOut` 在每次扣库存时都查询数据库判断 | 考虑使用数据库触发器或应用层批量处理 |

### 2.8 评价系统（DishEvaluationServiceImpl）

#### ✅ 优点
1. **评分范围校验**：1-5 星严格校验
2. **内容长度限制**：500 字符上限
3. **租户隔离**：所有操作都校验 `tenantId`
4. **防重复回复**：已回复的评价不能再次回复

#### ⚠️ 问题

| # | 严重度 | 问题描述 | 建议 |
|---|--------|----------|------|
| 1 | 🟢 低 | **缺少 XSS 防护**：评价内容和回复内容未做 HTML 转义 | 入库前对 `content` 和 `replyContent` 做 `StringEscapeUtils.escapeHtml4()` |
| 2 | 🟢 低 | **缺少评价频率限制**：同一用户对同一菜品可多次评价 | 建议增加唯一约束或频率限制 |

### 2.9 库存管理

#### ✅ 优点
1. **乐观锁扣减**：`WHERE stock_qty >= qty` 防止超卖
2. **自动停售/起售**：库存为 0 时自动标记停售，补货后自动恢复
3. **库存不足友好提示**：错误信息中包含当前库存和需求量

#### ⚠️ 问题

| # | 严重度 | 问题描述 | 建议 |
|---|--------|----------|------|
| 1 | 🟡 中 | **库存扣减 SQL 拼接**：`setSql("stock_qty = stock_qty - " + qty.toPlainString())` | 使用参数化查询或 MyBatis-Plus 内置方法 |
| 2 | 🟢 低 | **无库存预警机制**：库存低于 `min_stock` 时没有告警 | 建议增加库存预警通知（邮件/短信） |

## 三、数据库层面建议

| # | 建议 | 说明 |
|---|------|------|
| 1 | **购物车加唯一索引** | `(user_id, dish_id)` 或 `(user_id, setmeal_id)` 防止重复添加 |
| 2 | **订单号加索引** | `number` 字段加唯一索引，加速幂等查询 |
| 3 | **评价去重约束** | `(user_id, dish_id, order_id)` 唯一索引防止重复评价 |
| 4 | **订单表 `status` 加索引** | 后台按状态筛选高频操作 |
| 5 | **订单明细表 `order_id` 加索引** | 查询订单详情必用 |
