# Reggie AI 提示词循环开发系统

> 版本：v1.0 | 日期：2026-08-22 | 适用范围：Reggie 外卖系统（Spring Boot 2.4.5 + JDK 1.8 + MyBatis-Plus + Vue2 + Element UI）

## 1. 背景与目标

### 1.1 背景
本项目正以「大语言模型 + 人工把关」方式做循环式开发。当前已具备大量基础设施：
- **规范底座**：`AGENTS.md`（构建命令、技术栈、工程约定、crud-table 列对齐规范、Git 注意）
- **跨会话记忆**：`.codebuddy/memory/`（`MEMORY.md` 长期记忆 + 按日日志），是跨会话上下文的单一来源
- **强制约束**：JDK 1.8 语法硬约束、`mvn -o clean compile` 编译验证铁律、Vue2 Options API 唯一、前端令牌单一来源 `styles/tokens.css`
- **任务管理**：`todo_write` 工具可建立结构化任务清单

### 1.2 目标
建立**可持续运行直到可交付**的 AI 开发循环，让 AI 作为开发主体完成「需求分析 → 编码 → 测试 → 修复 → 优化」，人工仅担任产品负责人（定方向、把关、终止）。

### 1.3 设计原则
| 原则 | 含义 |
|---|---|
| 状态可追溯 | 一切决策、取舍、变更必须落盘到 memory / CHANGELOG，禁止"黑箱" |
| 验证有门禁 | 编译、测试、规范检查是循环闸门，未通过不得进入下一阶段 |
| 人工可控 | 每个循环设检查点，支持暂停、调整方向、重排优先级 |
| 收敛不发散 | 每个循环只处理一个功能单元；未做项显式记录，避免无限扩散 |
| 记忆即基线 | 每个循环开始先读记忆，结束时写入记忆，形成上下文闭环 |

## 2. 循环架构总览

```
┌────────────────────────── 一个开发循环（= 一次迭代） ──────────────────────────┐
│                                                                            │
│   ┌──→ [S0 状态感知] ──── 读记忆 + git 状态 → 输出《状态快照》                 │
│   │         ↓                                                             │
│   │   [S1 需求分析] ──── 拆解功能点 + 依赖清单 + 复用检查 → 输出《需求分析书》   │
│   │         ↓                                                             │
│   │   [S2 方案规划] ──── todo_write 任务分解 → 输出《实现计划》               │
│   │         ↓                                                             │
│   │   [S3 代码实现] ──── 按模块实现 + 标注修改点 → 输出《变更清单》            │
│   │         ↓                                                             │
│   │   [S4 测试验证] ──── 编译 + 测试 + 规范检查 → 输出《验证报告》             │
│   │         ↓                                                             │
│   │   [S5 缺陷修复] ──── 失败项定位根因 → 修复 → 回 S4（≤3 次）→《修复记录》   │
│   │         ↓                                                             │
│   │   [S6 审查优化] ──── 坏味道/安全/性能审查 → 输出《优化清单》              │
│   │         ↓                                                             │
│   │   [S7 记忆沉淀] ──── memory + CHANGELOG + git commit → 输出《变更记录》   │
│   │         ↓                                                             │
│   │   [S8 完成度评估] ── 对照验收标准评分 → 输出《完成度评估》                 │
│   │         ↓                                                             │
│   │   未达交付 → 取出遗留项/下一需求，开始下一循环 ─────────────┐              │
│   └──────────── 已达交付 → 进入交付状态 / 等待人工确认 ──────────┘              │
└────────────────────────────────────────────────────────────────────────────┘
```

### 2.1 循环粒度（重要）
- **一个循环 = 一个功能单元或一个缺陷修复**，不追求单次大而全。
- 大需求按「可独立验证的最小切片」拆成多个循环。
- 每个循环通常 1~3 个小时内可完成；超过则拆细。

## 3. 阶段定义与输入/输出格式

### S0 状态感知（Session Bootstrap）

**目的**：恢复跨会话上下文，建立本次循环基线。

**输入**：
- 工作区：`d:/MyCode/reggie`
- `AGENTS.md`、`.codebuddy/rules/前端.mdc`
- `.codebuddy/memory/MEMORY.md` + 最近 2 个日志文件
- `git status`、`git log -5 --oneline`
- 用户本次指令

**动作**：
1. 读取上述全部上下文；
2. 核对当前分支、未提交变更、构建状态；
3. 明确本次循环目标（用户指令优先，否则从遗留待办中按优先级选取）。

**输出**（必须按此格式）：
```markdown
【循环 #N 状态快照】
- 日期：YYYY-MM-DD
- 本次目标：<一句话>
- 当前分支：<branch>
- 未提交变更：<文件清单，或"无">
- 上次循环遗留：<清单，或"无">
- 本次循环任务：<todo 概要>
- 已知风险/阻塞：<清单，或"无">
```

---

### S1 需求分析

**目的**：把需求转化为可执行、可验证的功能点，杜绝模糊开发。

**输入**：S0 状态快照、用户需求原文。

**动作**：
1. 拆解为独立功能点（F1、F2…）；
2. 输出【依赖清单】（接口/数据/业务），逐项标注来源；
3. 复用检查：Java 查 `common/`、`module/*/service`、`dao`；前端查 `js/components.js`、`page/`、`styles/`；
4. 影响面分析：涉及模块、数据表、测试文件（新增表必须同步 `schema*.sql`）；
5. 冲突检查：与产品定位（连锁加盟总部私有化部署）是否一致、与现有规范是否冲突；
6. 显式列出**本次不做**的项（防过度设计）。

**输出**：
```markdown
【需求分析书】
- 需求名称：
- 背景与目标：
- 功能点清单：
  - F1：<描述>
    - 验收标准：<可测试的断言>
    - 涉及模块：<controller/service/mapper/model>
    - 数据依赖：<表/字段/Redis key>
    - 接口：<路径 + 方法>
- 依赖清单：
  - 接口依赖：<上游/下游接口>
  - 数据依赖：<表、迁移脚本名>
  - 业务依赖：<状态流转/事件>
- 复用检查结果：<已存在可复用：…；需新增：…>
- 影响面：<模块列表 + 测试文件列表>
- 风险与取舍：<含"本次不做"项>
```

---

### S2 方案规划

**目的**：把需求分析书拆成有序任务，全部落到 `todo_write`。

**输入**：需求分析书。

**动作**：
1. 任务分解为可独立验证的步骤（每步含目标文件 + 验证方式）；
2. 排定顺序与依赖（先表结构 → 后 Service → 再 Controller → 再前端）；
3. 每个任务标注「完成判据」。

**输出**：
```markdown
【实现计划】
- 任务 1：<描述>
  - 文件：<路径>
  - 完成判据：<如何确认做完>
- 任务 2：…
- 执行顺序与依赖：<说明>
- 预估循环数：<说明>
```
同时调用 `todo_write` 建立任务清单（此后每完成一项立即更新状态）。

---

### S3 代码实现

**目的**：按计划落地代码，严格遵守项目强制规范。

**输入**：实现计划 + `AGENTS.md` 全部约束。

**动作**：
1. 按模块分层实现（`com.reggie.module.<module>` 内 controller/service/mapper/model）；
2. 遵守强制规范：JDK 1.8 语法（禁 `var`/`List.of`/文本块等）、命名规范、注释（JavaDoc/docstring）、SLF4J 日志、参数校验、`PageUtils.of/cap` 分页、MyBatis-Plus `#{}`、租户忽略表走专用 Mapper；
3. 前端仅 Vue2 Options API，颜色走 `styles/tokens.css` 令牌，crud-table 列对齐走 `resolveColAlign`；
4. 每个改动点标注 `// 修改点：` 或 `# 修改点：`；
5. 新增表时同步产出迁移脚本 `db/migration/V<日期>__描述.sql` + 测试库 `schema-<module>.sql`。

**输出**：
```markdown
【变更清单】
- 变更文件：<列表>
- 核心改动：<逐文件说明>
- 新增接口/表/配置：<清单>
- 需人工注意：<迁移脚本执行、配置、联调依赖>
```

---

### S4 测试验证

**目的**：以门禁拦截回归，未通过不得进入下一阶段。

**输入**：变更清单。

**动作**（按顺序，全绿才算过）：
1. **编译铁律**：`mvn -o clean compile`（必须全量，勿信增量），`EXIT=0` 且无 `ERROR`；
2. **测试**：`mvn -o test`（H2 内存库，无需 MySQL；`@SpringBootTest` 需 Redis，可说明跳过项）；
3. **前端校验**：`node --check` 语法检查、grep 常见回归（`},\s*,` 空槽位、`<crud-dialog>` 配对）；
4. **规范检查**：JDK8 语法扫描、`System.out.println` 违规、硬编码路径/颜色、`align` 规范、`.box .el-table` 选择器陷阱等；
5. **自测样例**：正常 + 异常场景的最小验证。

**输出**：
```markdown
【验证报告】
- 编译：PASS / FAIL（错误明细）
- 测试：<用例数> 通过 / <失败数>（失败明细）
- 前端检查：PASS / 违规清单
- 规范检查：PASS / 违规清单
- 未验证项：<需联调/需真机/需人工确认>
```

---

### S5 缺陷修复

**目的**：把验证报告中的失败项修到全绿，且只修根因。

**输入**：验证报告。

**动作**：
1. 逐条定位根因（用调试工具/日志/最小复现，禁止猜）；
2. 修复并回到 S4 重新验证；
3. 单点重试上限 3 次，超限 → 升级人工介入（见 §5）。

**输出**：
```markdown
【修复记录】
- 缺陷：<现象>
- 根因：<一句话根因>
- 修复：<文件+位置+方式>
- 回归：<复验结果>
- 关联影响：<是否影响其他链路>
```

---

### S6 审查与优化

**目的**：质量兜底，把坏味道/隐患分级处理。

**输入**：本次循环全部变更。

**动作**：审查安全（鉴权注解、参数校验、SQL 注入、XSS）、性能（N+1、批量操作、分页透传）、规范符合性（对齐、命名、注释）、可维护性。

**输出**：
```markdown
【优化清单】
- P0 必须修（本轮完成）：<项>
- P1 建议（记入下轮）：<项>
- P2 可延后（记入待办）：<项>
```

---

### S7 记忆沉淀

**目的**：把本次循环的经验变成下一次循环的上下文，形成正反馈。

**动作**：
1. 追加 `.codebuddy/memory/YYYY-MM-DD.md`（今日文件，不存在则创建）：
   - 完成的功能/修复（含根因与取舍）
   - 新增的表/接口/迁移脚本
   - 踩坑与认知更新
2. 长期事实更新进 `MEMORY.md`（产品定位、易回归点、规范变更）；
3. 更新 `CHANGELOG.md`（格式：`2026-08-22 | 模块 | 更新内容 | 开发者：AI`）；
4. `git commit`（仅当用户允许；信息按 `feat:/fix:/refactor:` 前缀）。

**输出**：
```markdown
【变更记录】
- memory 更新：<条目>
- CHANGELOG：<条目>
- commit：<hash + message>（如有）
```

---

### S8 完成度评估（Gate）

**目的**：判定"是否可交付 / 继续循环 / 需人工介入"。

**输入**：S1~S7 全部产物。

**动作**：按 §4 评分表逐维打分，输出判定。

**输出**：
```markdown
【完成度评估】
- 功能完成度：<百分比 + 对照验收标准逐项说明>
- 质量完成度：<百分比 + 编译/测试/规范结果>
- 交付准备度：<百分比 + 文档/迁移/联调清单>
- 未完成项：<清单 + 原因 + 建议去向>
- 判定：可交付 ✅ / 继续循环 🔁 / 需人工介入 ⚠️
- 下一循环建议目标：<若有>
```

## 4. 完成度判断标准（评分表）

每个维度按 0~100% 打分，规则如下：

### 4.1 功能完成度
| 分值 | 判据 |
|---|---|
| 100% | 需求分析书全部功能点通过验收标准 |
| 80% | 核心功能点全过，边缘场景有未覆盖（已记录） |
| 60% | 主流程可用，存在已知未实现功能点 |
| <60% | 主流程不通，须继续循环 |

### 4.2 质量完成度
| 项 | 通过判据 | 权重 |
|---|---|---|
| 编译 | `mvn -o clean compile` EXIT=0 无 ERROR | 强制门禁 |
| 测试 | 新增逻辑有对应测试，失败为 0 | 强制门禁 |
| 规范 | 无 JDK8 语法/命名/对齐/令牌违规 | 强制门禁 |
| 安全 | 鉴权注解正确、参数校验、无注入风险 | 强制门禁 |
| 审查项 | P0 清零 | 强制门禁 |

### 4.3 交付准备度
| 项 | 判据 |
|---|---|
| 迁移脚本 | 新增表/字段有 `V<日期>__*.sql` 且同步测试库 |
| 文档 | CHANGELOG 已更新，函数/接口注释齐全 |
| 联调说明 | 新增/变更接口有前端联调信息 |
| 记忆 | memory 已沉淀，遗留项已记录 |

### 4.4 判定矩阵
| 功能 | 质量 | 交付准备 | 判定 |
|---|---|---|---|
| ≥80% | 全绿 | ≥80% | **可交付** ✅（或按计划进入下一循环） |
| ≥60% | 全绿 | ≥60% | 继续循环 🔁（下一循环消化遗留） |
| 任一 <60% 或质量门禁未过 | — | — | 继续循环 🔁（修复直至全绿） |
| 功能不明/规范冲突/卡死 | — | — | **需人工介入** ⚠️ |

## 5. 人工介入与方向调整

### 5.1 检查点
- **每循环结束**：S8 输出后停 1 次，向人工汇报评估结果与下一循环建议，人工可确认或调整。
- **强制审批点**（AI 不得自行执行）：
  - 破坏性变更（删表/删列/清数据）
  - 修改 `pom.xml` 依赖版本
  - 对外接口变更（路径/入参/出参）
  - 新建迁移脚本落地到生产库
  - git commit / push

### 5.2 人工干预指令（可直接粘贴给 AI）
```markdown
【方向调整】当前循环目标改为：<新目标>
【优先级重排】<A> 优先于 <B>
【范围收缩】暂停 <X>，只做 <Y>
【终止循环】停止当前循环，保留已完成工作并沉淀记忆
【忽略规范】本次豁免：<具体规范项>（理由：…）
【人工补充】补充信息：<任何上下文>
```

### 5.3 异常升级规则（AI 自动触发人工介入）
| 情形 | 动作 |
|---|---|
| 同一缺陷修复 ≥3 次仍失败 | 停止并上报根因分析 |
| 编译/测试出现环境性问题（Redis、MySQL 不可用） | 说明环境要求，请求人工准备 |
| 需求存在二义性且影响实现方向 | 用 `ask_followup_question` 提问，不得擅自假设 |
| 改动与产品定位（私有化/加盟总部）冲突 | 停止并上报 |
| 循环超过 1 个功能切片 | 拆细，已做部分先沉淀记忆 |

## 6. 循环终止条件

循环持续运行，直到满足任一终止条件：
1. **达到可交付**：S8 判定"可交付"且人工确认；
2. **人工终止**：下达【终止循环】指令；
3. **迭代上限**：达到人工设定的最大循环数或日期（如"本周跑到周五为止"）。

终止后 AI 必须执行 S7 记忆沉淀（否则上下文断链）。

## 7. 与本项目基础设施的集成

| 现有设施 | 循环中的用法 |
|---|---|
| `AGENTS.md` | S0 必读；S3 强制遵守（JDK8、构建、crud-table 对齐、Git 注意） |
| `.codebuddy/memory/` | S0 读取（MEMORY.md + 近 2 日日志）；S7 写入 |
| `.codebuddy/rules/前端.mdc` | 前端改动时 S3 强制遵守 |
| `todo_write` | S2 建立任务；S3 每完成一项更新 |
| `db/migration/` | 新增表/字段产出参考脚本（手动执行，非自动迁移） |
| `mvn -o clean compile` | S4 编译铁律 |
| `docs/CODE_STANDARDS.md` | S3/S6 规范参照 |
| 产品定位（MEMORY.md §1） | S1 冲突检查依据 |

## 8. 可直接复用的提示词模板

### 8.1 循环启动提示词（每次新会话/新循环开始时粘贴）
```markdown
你现在是 Reggie 外卖系统的持续开发循环引擎。项目路径 d:/MyCode/reggie。
请严格按 docs/AI_LOOP_SYSTEM.md 的循环流程执行。

【第 1 步】执行 S0 状态感知：
- 读取 AGENTS.md、.codebuddy/memory/MEMORY.md 及最近 2 个日志文件
- 执行 git status、git log -5 --oneline 查看当前状态
- 输出《状态快照》

【第 2 步】明确本次目标：
- 若我未指定目标，从最近日志的"遗留项/待办"中按优先级选取 1 个可独立验证的功能切片，并说明选择理由

【第 3 步】开始循环：S1 需求分析 → S2 规划（todo_write）→ S3 实现 → S4 验证（编译铁律 mvn -o clean compile）→ S5 修复 → S6 优化 → S7 记忆沉淀 → S8 完成度评估

【循环纪律】
```

# 附录 A：全项目自动化改造模式（单体架构·大厂标准）

> 适用场景：用户要求 AI **自动完成项目规划**，并自动修复/完善**所有功能**，按一线互联网公司开发标准执行，目标为**单体架构下的高质量交付**（非微服务拆分）。

## A.1 模式定位与边界

**这是本循环系统的「全量巡航」变体**，在标准 S0~S8 循环之上叠加一条**领域主线**：AI 不再等单点需求，而是先对单体项目做整体诊断，再按优先级自动逐域改造，每域一次独立循环，全程持续直到所有域达标。

**关键边界（避免 AI 自作主张翻车）**：
| 维度 | 规则 |
|---|---|
| 架构形态 | **保持单体**。严禁引入微服务、服务注册发现、消息总线、分布式事务等跨进程架构改造 |
| 技术栈 | **锁死 Spring Boot 2.4.5 + JDK 1.8 + MyBatis-Plus 3.4.2**。禁止升级到 3.x / Jakarta / JDK 17 |
| 数据库 | 保持单库单租户隔离插件；新增表必须同步迁移脚本 + 测试库 `schema*.sql` |
| 前端 | 保持原生 JS Vue2 + Element UI；禁止引入 Vite / TypeScript / Composition API |
| 破坏性 | 删除/重命名公开接口、改表名/列名需人工审批（见 §5.1） |

## A.2 六维改造目标（大厂质量门禁）

每域改造后，S4 验证必须覆盖以下六维。任一维度不达「基线」不得进入下一域。

### 1) 代码结构优化
- 分层严格：controller / service / service.impl / mapper / model(dto/entity/vo) / common / config 职责清晰，禁止跨层调用（controller 直调 mapper、service 操作 SQL 等）
- 包按业务域（`module.*`）而非技术层堆砌；每个类单一职责，方法 ≤80 行（Java）/≤60 行（Python）
- 消除重复代码（抽公共 util / 父类 / 模板方法）；magic number 提取为常量或配置
- 统一 DTO/VO/Entity 边界，禁止 Entity 直接透传前端

### 2) 模块解耦
- 域内高内聚、域间低耦合；跨域调用走 service 接口而非直接注入实现细节
- 消除循环依赖（Spring Bean 循环引用安检）
- 通用能力（鉴权、限流、日志、脱敏、异常处理）下沉 `common/` 与 `aspect/`，禁止散落业务代码
- 配置外部化（Nacos/加密 yml），禁止硬编码敏感信息与路径

### 3) 性能优化
- 高频查询加缓存（Redis，设 TTL + 防穿透/击穿），缓存一致性有策略
- 列表查询强制 `PageUtils.of/cap` 封顶；禁止 `pageSize:999` 拉全量
- 批量写入（MyBatis-Plus `saveBatch`/批量 SQL），禁止循环单条 insert
- N+1 消除（join / 批量预加载）；慢 SQL 巡检（explain）
- 前端虚拟滚动 + 骨架屏；大响应分页/懒加载

### 4) 安全加固
- 鉴权三件套（`@RequiresAdmin` / `@RequiresPermission` / `@RequireEmployee`）正确落地，混合端点方法级注解
- 所有入参校验（Controller Bean Validation + Service 业务校验），绝不信任前端
- SQL 注入：MyBatis `#{}`、原生 SQL 参数化；XSS：HtmlUtil.escape（Java）/ 前端禁未清洗 `v-html`
- 敏感信息脱敏（日志、接口返回）；密钥/配置不入库、不进版本
- 高危操作二次确认；限流/防爆破（已有 `BruteForceProtectionFilter` / `ApiPerformanceMonitorAspect` 须保留并完善）

### 5) 可维护性提升
- 全量 JavaDoc / docstring；复杂逻辑有注释；修改点标注 `// 修改点：`
- 统一异常体系（`com.reggie.common` 全局异常处理 + 业务异常码），禁止吞异常 / `catch(Exception)`
- 结构化日志（SLF4J + MDC），禁止 `System.out.println` / `print`
- 关键链路可观测（traceId、耗时埋点）；可回滚（事务边界清晰、幂等设计）
- 完善的 CHANGELOG + 跨会话 memory 沉淀

### 6) 代码规范统一
- JDK 1.8 语法铁律（禁 `var`/`List.of`/文本块/`switch` 表达式/`record`）
- 命名规范（PascalCase 类、camelCase 方法、UPPER_SNAKE_CASE 常量）、单行 ≤120 字符、嵌套 ≤3 层
- 前端令牌单一来源 `styles/tokens.css`；crud-table 列对齐走 `resolveColAlign`；选择器陷阱规避（`.tableBox.el-table`）
- 提交信息规范 `feat/fix/refactor/...`；禁止临时文件进版本

## A.3 自动诊断 → 自动规划 → 自动执行

**第一个循环（S0~S2 的特殊扩展）做「全项目体检 + 六维路线图」**：

AI 必须完成：
1. 用 `list_dir` / `search_content` / `lsp` 扫描全部 `src/main/java` 与 `src/main/resources` 前端，统计：类数量、包结构、循环依赖风险、重复代码、超大方法、缺失校验/异常的端点、裸 SQL、硬编码、缺测点
2. 按六维逐项打**现状分（0~100）**与**差距清单**
3. 输出《全项目改造路线图》，按风险/收益排序成**领域队列**，例如：
   ```
   域1 基础设施与规范底座（common/异常/日志/配置）—— 前置依赖，先修
   域2 安全与鉴权（RBAC/参数校验/注入/XSS/脱敏）—— 高危，先修
   域3 门店与加盟（store_info/franchise）—— 业务核心
   域4 会员与交易（member/coupon/cashier/order）—— 资金链路
   域5 商品与营销（dish/setmeal/category/promotion）
   域6 进销存与报表（inventory/report）
   域7 性能与缓存（Redis 化高频 + 慢 SQL）
   域8 前端工程化（令牌/对齐/虚拟滚动/骨架屏）
   域9 测试与文档（补齐单测 + CHANGELOG）
   ```
4. 每域独立走一遍 S1~S8（需求分析书→实现计划→实现→验证→修复→优化→记忆→评估）
5. 每域结束把「现状分 → 改造后分」写回路线图；全部域跑完做 S8 总评估

## A.4 自动执行纪律（防跑偏）

- **每域一次编译门禁**：S4 必须 `mvn -o clean compile` 全量通过，不得累积多域再编译
- **每域一次 memory 沉淀**：`YYYY-MM-DD.md` 记录该域改动 + 六维得分变化

- **遇破坏性变更先停**：列清单交人工，不得擅自删表/改公开接口
- **卡死即上报**：单点修复 ≥3 次失败、或某域风险超出单体改造范围，停止并给出人工决策建议

## A.5 完成度判定（全项目级）

S8 总评估对照六维门禁，全部达基线即判定**「单体架构·大厂标准交付就绪」**：

| 模块解耦 | 0 循环依赖，通用能力 100% 下沉 common |
| 性能 | 列表 100% 分页封顶，N+1 清零，已识别慢 SQL 全部治理 |
| 安全 | 所有写端点有鉴权+校验，0 裸 SQL，敏感信息 100% 脱敏 |

| 规范 | JDK8/命名/前端令牌/对齐违规 0 项；CHANGELOG 连续 |
